# Architectural Decision Records (ADRs)

This log records major architectural and technical decisions made for Autonomous SDR V2. Decisions must not be silently reversed without adding a new ADR explaining why.

---

### ADR-001: Multi-Business Abstraction Layer
* **Status:** `ACCEPTED` | **Date:** 2026-08-25 | **Phase:** Phase 02
* **Context:** The legacy codebase had hardcoded assumptions about "Devcomm" (training/road safety). The new requirement is to support Bloomy Digital Studio (website sales) as well as B2B consulting and other offers using the exact same generic SDR engine.
* **Decision:** Introduce a formal hierarchical structure: `Workspace` → `Business` → `Offer` → `Campaign`. Generic SDR services interact only with these generic abstractions.
* **Alternatives Considered:** Separate codebases/forks per business (rejected due to maintenance overhead) vs. Single business with tag switches (rejected as unscalable).
* **Consequences:** All database queries, sender identities, knowledge bases, and calendars must be scoped to `workspaceId` and `businessId`.

### ADR-002: Pluggable Signal Providers vs. Hardcoded Web Crawling
* **Status:** `ACCEPTED` | **Date:** 2026-08-25 | **Phase:** Phase 04
* **Context:** Bloomy Digital Studio requires auditing PageSpeed, CMS, and e-commerce signals. B2B corporate consultancies require auditing employee growth, multi-site scale, and hiring signals.
* **Decision:** Implement a pluggable `SignalProvider` registry interface. Campaigns dynamically declare which signal providers to execute. Website technical auditing is implemented as a pluggable signal module, NOT hardcoded into the generic SDR engine.
* **Alternatives Considered:** Monolithic company research worker running all scrapers for all leads (rejected due to wasted API credits and irrelevant data).
* **Consequences:** Adding new data sources (e.g. LinkedIn job scraper, BuiltWith) requires only implementing a new `SignalProvider` class without modifying core SDR orchestration.

### ADR-003: Instantly.ai V2 Webhooks vs. Polling Synchronization
* **Status:** `ACCEPTED` | **Date:** 2026-08-25 | **Phase:** Phase 09
* **Context:** The legacy system polled the Instantly API hourly for boolean `replied: true`, which was slow, missed reply email bodies, and caused rate-limit bottlenecks.
* **Decision:** Implement real-time inbound webhook ingestion for Instantly reply events (`POST /api/webhooks/instantly`) with HMAC signature verification and idempotency caching. Retain hourly polling strictly as a fallback reconciliation mechanism.
* **Alternatives Considered:** Direct IMAP/SMTP mailbox integration (rejected due to complex multi-mailbox warmup and deliverability management).
* **Consequences:** Instant reply classification and rapid conversational responses become possible.

---

### ADR-004: Server-Side Secret Management via GCP Secret Manager
* **Status:** `ACCEPTED` | **Date:** 2026-08-25 | **Phase:** Phase 01
* **Context:** Legacy Firestore rules allowed authenticated clients to read plaintext API keys stored in `settings/aiSecrets` and `settings/integrationSecrets`.
* **Decision:** Move all sensitive third-party API keys to Google Cloud Secret Manager (or secure server environment variables) and configure Firestore rules to forbid all client reads (`allow read: if false;`).
* **Alternatives Considered:** Obfuscating keys in Firestore (rejected as insecure).
* **Consequences:** API keys are never exposed in browser network inspection or client SDK snapshots.

### ADR-005: Two-Pass Evidence-Grounded Copywriting
* **Status:** `ACCEPTED` | **Date:** 2026-08-25 | **Phase:** Phase 08
* **Context:** LLMs are prone to hallucinating company details (e.g. inventing client names or employee numbers) if website text is sparse.
* **Decision:** Outreach generation operates in two passes:
  1. Copywriter generates draft from verified `EvidenceItem[]`.
  2. `validateOutreachClaims` verifies that every specific factual claim matches an evidence item with `confidence >= 70`. If unverified claims exist, the draft is rewritten or flagged.
* **Alternatives Considered:** Strict string template substitution (rejected as robotic and unnatural).
* **Consequences:** Outreach copy reads naturally while remaining 100% truthful and grounded in real evidence.

### ADR-006: Microsoft Graph Direct OAuth2 vs. Third-Party Scheduling Layers
* **Status:** `ACCEPTED` | **Date:** 2026-08-25 | **Phase:** Phase 12
* **Context:** Outlook Calendar is the primary business calendar used by the operator.
* **Decision:** Retain and extend the existing working Microsoft Graph integration for querying free/busy availability and booking meetings, wrapped in a generic `CalendarProvider` abstraction to allow adding Cal.com or Google Calendar in the future.
* **Alternatives Considered:** Forcing all prospects to use Calendly links only (rejected because conversational booking dramatically increases conversion rates).
* **Consequences:** Real-time conversational slot negotiation is supported directly in email threads.

### ADR-007: Deterministic Fast-Path for Unsubscribe & OOO with LLM Reply Intelligence
* **Status:** `ACCEPTED` | **Date:** 2026-08-25 | **Phase:** Phase 10
* **Context:** Legal and compliance mandates (GDPR, CAN-SPAM) require instant suppression when prospects ask to unsubscribe. Relying purely on an LLM for unsubscribe detection introduces unnecessary API latency, cost, and occasional prompt misinterpretation.
* **Decision:** Implement a two-pass architecture:
  1. **Deterministic Fast-Path**: High-precision regex pattern matching for French and English unsubscribe requests and Out-of-Office auto-responders. If matched, triggers immediate suppression / suppressionList insertion with 100% confidence and zero LLM delay.
  2. **Structured LLM Intent & Objection Classification**: Untrusted prospect email text is enclosed in `<untrusted_prospect_input>` XML tags with strict anti-injection prompting, validated against a Zod schema returning structured intent, fine-grained objection categories (`PRICE`, `EXISTING_PROVIDER`, `NO_BUDGET`, `NOT_PRIORITY`, `BAD_TIMING`, `NO_TIME`), confidence scores, and question extraction.
* **Alternatives Considered:** Pure LLM classification for all inbound emails (rejected due to latency and risk of prompt injection bypassing unsubscribe handling) vs. purely keyword-based rule engine (rejected as insufficient for nuanced objections and buying signals).
* **Consequences:** Zero-delay compliance for unsubscriptions alongside rich, resilient classification for complex conversational replies.

### ADR-008: Multi-Business Dual-Fixture Automated Simulation & Static Invariance Testing
* **Status:** `ACCEPTED` | **Date:** 2026-08-25 | **Phase:** Phase 16
* **Context:** Autonomous SDR V2 was architected to support completely disparate business models (Bloomy Digital Studio selling web development and Devcomm B2B Consulting selling sales coaching) without custom codebase branching. Automated verification is needed to prove that adding or running any new business model requires zero code changes in generic SDR services.
* **Decision:** Implement a programmatic dual-fixture simulation engine (`functions/src/tests/fixtures/e2e-fixture-runner.ts`) along with a static regex scanner test (`functions/src/tests/e2e/zero-code-change-assert.test.ts`) that asserts:
  1. **Signal Divergence**: Website audits are actively selected for Bloomy and completely omitted for Devcomm consulting.
  2. **Persona Divergence**: Matches Owner for Bloomy and Directeur Commercial for Devcomm.
  3. **Strict Cross-Tenant Isolation**: Knowledge bases, pricing guardrails, and offers are isolated by `workspaceId`/`businessId`.
  4. **Static Invariance**: Zero hardcoded business branching (`if (business === "Bloomy")` or `if (businessId === "biz_bloomy")`) exists across all 25+ generic SDR service files.
* **Alternatives Considered:** Manual testing through UI (rejected as non-repeatable and error-prone) vs. maintaining separate test configurations (rejected as failing to verify cross-tenant genericity).
* **Consequences:** Continuous CI/CD guarantee of true multi-business genericity and zero-regression tenant isolation.

### ADR-009: Progressive Disclosure UX — Four Primary Surfaces with a Preserved Advanced Section
* **Status:** `ACCEPTED` | **Date:** 2026-08-26 | **Phase:** Phase 18
* **Context:** The backend is deliberately powerful (100+ services, 10 providers, queues, scoring, state machines), and the frontend had been mirroring that complexity: 13 navigation entries organised as the internal pipeline (`STEP 1 — FIND` → `STEP 2 — RESEARCH` → `STEP 3 — ENGAGE`), a metrics dashboard as the landing page, and nine manual verbs (Create, Run, Research, Find contact, Generate, Approve, Send, Sync, Run queue) between a user's intent and a sent email. The product read as an internal admin/CRM tool rather than an autonomous SDR a small-business owner could hire.
* **Decision:** Restructure the experience into four progressive-disclosure levels without rewriting backend services:
  1. **Level 1 — Home / Campaigns / Inbox / Meetings.** One natural-language field is the primary interaction; the AI-derived targeting is confirmed in plain language ("WHO / WHERE / I'LL PRIORITIZE / I'LL CONTACT / OBJECTIVE") rather than as ~30 configuration fields.
  2. **Level 2 — campaign and prospect detail**, organised around *why we are contacting them* (derived from `OpportunityScore` evidence) rather than raw database fields.
  3. **Level 3 — Settings**, grouped into My business / SDR / Advanced, with a new plain-language autonomy control writing `business.automationPolicy.mode`.
  4. **Level 4 — `/app/advanced`**, where all pre-existing operational tooling (Companies, Contacts, Research, Emails, Campaign builder, Imports, Analytics, System logs, plus the automation toggle and manual research run) is **moved, not deleted**.
  A translation layer (`src/lib/sdr/activity-humanizer.ts`, `opportunity-language.ts`, `inbox-filters.ts`) is the single boundary where technical event types, qualification states and conversation statuses become user language; an aggregation layer (`src/lib/sdr/aggregations.ts`) keeps business logic out of React components.
* **Alternatives Considered:**
  * *Deleting the operational pages* — rejected: they remain necessary for debugging and power-user operations (Golden Rule: preserve working code).
  * *Simplifying the backend to match the simplified UI* — rejected: the intelligence is the product's value; only its presentation was the problem.
  * *Rendering `log.message` directly in the activity feed* — rejected: backend messages are technical by design (`"Outreach sent to Instantly.ai. Campaign: ..."`). The humanizer reads only `type` + `metadata`, so provider names can never leak into a primary surface.
* **Consequences:** A non-technical owner reaches a live campaign in two meaningful interactions (describe → confirm & start) and never encounters SIRENE, NAF, Dropcontact, Instantly, PageSpeed, queues or provider APIs on a primary surface. Campaigns are created `active` with `autoQueueHighScoreCompanies: true` and run immediately, so the existing scheduled jobs carry the pipeline forward under the business autonomy policy. Power-user capability is fully retained one click away under Advanced.

### ADR-010: Client Read Access to `conversations` with Server-Only Writes
* **Status:** `ACCEPTED` | **Date:** 2026-08-26 | **Phase:** Phase 18
* **Context:** `firestore.rules` declared no `match /conversations/{id}` block, so the catch-all `match /{document=**} { allow read, write: if false; }` denied all client access. The SDR Inbox reads conversations client-side (`listInboxConversations`, `getUnreadHumanAttentionCount`), meaning the Inbox and its attention badge could not function against real security rules — the simplified Inbox depends on that same data.
* **Decision:** Add an explicit rule granting `allow read: if signedIn();` on `conversations` and its `messages` subcollection, with `allow write: if false;`. All conversation mutations already flow through authenticated server-side callables (`takeOverConversationCallable`, `updateConversationStatusCallable`, `sendManualReplyCallable`, `approveAndSendReplyCallable`).
* **Alternatives Considered:** Routing every Inbox read through a new callable (rejected: a larger backend change for this UX phase, and inconsistent with `companies`/`contacts`/`outreach`, which already grant signed-in read); granting `allow write: if signedIn()` for symmetry with `outreach` (rejected: conversation state must not be forgeable from the client).
* **Consequences:** The Inbox reads real data under production rules. Conversation state is strictly server-authored — a tighter posture than the existing `outreach` rule. No secret material is exposed: API keys and webhook secrets live in `settings/aiSecrets` and `settings/integrationSecrets`, which remain `allow read, write: if false;`.

### ADR-011: PageSpeed Timeout Exception & Immediate Post-Discovery Research
* **Status:** `ACCEPTED` | **Date:** 2026-08-26 | **Phase:** Phase 18 (live-run remediation)
* **Context:** Two defects kept the SDR from producing usable results on live campaigns.
  1. **Timeouts.** `.claude/rules/provider-integrations.md` caps external HTTP timeouts at 8–15s. The PageSpeed provider used 8s and the signal coordinator bounded every provider at 10s. Measured against real French salon sites, PageSpeed Insights takes **30–40s** because Lighthouse renders the page server-side — and *the slower the prospect's site, the longer it takes*, so the highest-value prospects were the most reliably cut off. Every run aborted, the audit produced zero evidence, and an aborted audit is indistinguishable from "this site is fine". Speed is the measurable half of a website-modernisation offer, so the product's core claim could never be evidenced.
  2. **Scheduling.** Discovery ran immediately on campaign launch, but research only ran via the once-daily 08:00 job. A campaign started in the afternoon showed no movement for ~16 hours, which reads as broken.
* **Decision:**
  1. Introduce an optional `timeoutMs` on `SignalProvider`; the coordinator honours it (`provider.timeoutMs ?? timeoutMs`). PageSpeed declares 75s with a 60s fetch bound. This is a **documented, provider-specific exception** to the 8–15s rule, which continues to apply to every other integration. The 429 path keeps exponential backoff and now returns an actionable message naming the missing Google API key.
  2. Discovery enqueues `TASK_PIPELINE_COMPANY` per auto-queued company, so the existing 5-minute queue worker starts research within minutes instead of the next morning. Companies enqueued this way have `needsResearch` cleared so the daily sweep cannot double-process them; if enqueueing fails, the flag is left set and the daily job remains the fallback. The worker's own timeout moved from 120s to 540s so a batch of slow audits is not cut off mid-flight.
* **Alternatives Considered:** Keeping the 8–15s cap and dropping PageSpeed (rejected — it removes the only quantitative "your site is slow" evidence, and Invariant 5 requires claims to map to verified evidence); running PageSpeed in a separate long-running job (rejected as disproportionate — the queue worker already provides the execution boundary); raising the coordinator's global timeout for all providers (rejected — it would let genuinely stuck fast providers hold up a batch).
* **Consequences:** Website speed and LCP become real evidence. On the first live Paris campaign, re-scoring with PageSpeed active moved four salons from 37/49/62/70 to 59/58/77/79, all four crossing into `QUALIFIED` with specific, citable reasons ("Vitesse mobile critique (PageSpeed 26/100)", "Temps de chargement LCP élevé (29.6s)"). Campaigns now show progress within minutes of launch. `functions/src/tests/signals/provider-timeouts.test.ts` pins the exception so the bound is not tightened back.

### ADR-012: Contact Form as an Outreach Channel, With Refusal Encoded in Code
* **Status:** `ACCEPTED` | **Date:** 2026-08-28 | **Phase:** Phase 18 (channel expansion)
* **Context:** A large share of the small businesses the SDR is pointed at publish no email address anywhere — not on the site, not on Facebook, not in the mentions légales. Measured on nine real French shop sites: 1 plain HTML form, 3 CAPTCHA-protected, 1 third-party JS widget, 4 no form on the homepage (understated — only the homepage was fetched). Those prospects were reaching the end of the pipeline as "no contact found" and being dropped, even though the business had published a form whose entire purpose is to invite contact. A message sent through a form also lands in the inbox the owner themselves configured, bypassing spam filtering.
* **Decision:** Add `contact_form` as a third channel alongside `email` and `social_dm`, off by default and enabled per campaign from the plan-review screen. The pipeline falls through to it only when no email was found. Four refusals are encoded in the service rather than left to the caller or to configuration:
  1. **A CAPTCHA is a refusal.** reCAPTCHA, hCaptcha, Turnstile and friends mark the form assisted-only. It is never solved, outsourced, or worked around.
  2. **Honeypot fields stay empty.** A hidden input carrying a value is a framework token and is echoed back; a hidden input with no value is a trap and is skipped.
  3. **One message per company, ever** (`company.contactFormSentAt`). A second submission is indistinguishable from spam whatever it says.
  4. **A real reply address is required.** Without a resolvable sender the send is skipped, because a prospect who cannot answer or object is being spammed, not contacted.
  Safe mode blocks submission outright — a form has no address to check against the test allowlist, so the only honest containment is refusal — and the suppression list is checked by domain and SIREN before posting. Copy is written by the existing DM writer: both channels are short, unsubjected, and land in a personal inbox. The draft is queued for approval like any other, so nothing posts without a person deciding.
* **Alternatives Considered:** Headless-browser submission to cover JS-rendered and CAPTCHA'd forms (rejected — it is precisely the bot behaviour the CAPTCHA exists to stop, and it would put the sending domain in bad company); submitting without approval when autonomy is `auto` (deferred — the channel is new and unmeasured, and an unreviewable channel is the wrong place to start); scraping the form and emailing the address behind it (rejected — the address is not published, and using it is a different consent question).
* **Consequences:** Companies with a form but no email now produce a reviewable draft instead of dropping out. `functions/src/tests/outreach/contact-form.test.ts` pins the refusals — honeypot skipped, token echoed, unrecognised fields never invented, unusable form never guessed at — so the restraint cannot be quietly optimised away. The assisted path is not a failure state: a CAPTCHA'd form still yields a direct link and a ready-to-paste message, which is the same deal the DM channel offers.

### ADR-013: Never Infer State From Data That Failed To Load; Approvals Is Not Mode-Gated
* **Status:** `ACCEPTED` | **Date:** 2026-08-28 | **Phase:** Phase 18 (correctness remediation)
* **Context:** The owner reported that after a deploy the app showed their SDR as sending on its own, although they had saved "Draft only". Firestore was checked directly: `biz_bloomy.automationPolicy` held `{ mode: "manual", requireApprovalBeforeSend: true }`. The saved value was never lost — the interface was asserting something it had not read. Three defects combined:
  1. `listBusinessesClient` caught every error and returned `[]`. The caller treats zero businesses as "the workspace is empty" and **seeds hardcoded defaults**, so a transient read failure — a token refresh, a rules deploy propagating, a dropped connection — would have merge-written `DEFAULT_DEVCOMM` and `DEFAULT_BLOOMY` over real businesses, `automationPolicy` included. It had not fired yet; it was one bad moment away.
  2. `BusinessProvider`'s own catch substituted those same two hardcoded businesses in memory, so an unreadable workspace rendered as a business carrying `mode: "assisted"` that the owner had never configured.
  3. `approvalsEnabled(undefined)` returns `false`, and the Approvals page turned that into the sentence *"Your SDR sends on its own — right now this business lets the SDR send without asking."* Before the business record loaded, and whenever the read failed, the app stated an autonomy level as fact from missing data.
* **Decision:** "Could not read" and "there is nothing there" must stay distinguishable. `listBusinessesClient` throws; the provider catches, sets `loadError`, and substitutes nothing; a `WorkspaceLoadError` banner says plainly that nothing on screen reflects saved settings, with a retry. Seeding may only run after a *successful* read that returned zero. Separately, the Approvals surface is no longer gated on autonomy at all: the direct-message and contact-form channels always produce a draft a person must send, so gating removed those drafts from the interface entirely — written, queued, and never seen.
* **Alternatives Considered:** Keeping the in-memory defaults but stripping `automationPolicy` (rejected — the rest of the fabricated business is equally untrue); showing Approvals only when it has items (rejected — an empty queue is information, and the surface must be reachable to explain itself); defaulting `approvalsEnabled(undefined)` to `true` (rejected — it treats missing data as a different guess rather than as missing).
* **Consequences:** An unreadable workspace now fails visibly instead of rendering confident wrong settings. The destructive re-seed path is closed. `src/tests/read-cost.test.ts` pins all three: the catch block may not name the defaults, `listBusinessesClient` may not contain a `catch`, and neither navigation component may import `approvalsEnabled`.

### ADR-014: Firestore Read Cost Is Driven By Browsing, Not By Prospecting
* **Status:** `ACCEPTED` | **Date:** 2026-08-28 | **Phase:** Phase 18 (cost remediation)
* **Context:** The owner reported blowing through Firebase free quota within three days of light testing. Measured from Cloud Monitoring on the live project: document reads went **101/day (22–25 Aug) → 8,834 → 19,535 → 73,922**, past the 50,000/day free allowance, while writes stayed at 9,478 against a 20,000 allowance. Functions compute was *not* the problem — 4,052 billable instance-seconds/day is roughly 20% of the free tier, and 372 requests/day is 0.02% of it. Artifact Registry sits at 766 MB against 500 MB free, which is real but costs about €0.03/month. The cost was reads, and reads were tracking navigation: with 123 companies, 62 outreach, 43 conversations and 20 meetings, one screen cost ~250 reads and the sidebar's draft badge re-read all 62 outreach documents on **every** navigation, just to display a number. The earlier cost analysis named this as a risk ("vos écrans lisent encore des collections entières") but never quantified it, and the €15–30/month infrastructure line was an estimate, not a measurement.
* **Decision:** Three changes, none of which alter what any screen shows. (1) A 30-second read cache (`src/lib/sdr/query-cache.ts`) with in-flight de-duplication — concurrent callers share one round trip, and a repeat within the window is served from memory. (2) The draft badge uses `getCountFromServer` instead of reading the collection: billed at one read per 1000 index entries rather than one per outreach document ever created, with the composite index declared in `firestore.indexes.json`. (3) The approvals list queries `status == "draft"` instead of fetching all outreach and filtering in memory. Anything that writes calls `invalidateReadCache()`, so a cached read can never hide an action the user just took.
* **Alternatives Considered:** Server-side rollup documents updated by the existing jobs (deferred — the correct end state, but it moves the funnel's definition into a write path and needs backfill; the cache buys the same relief today); a longer TTL (rejected — cached data that outlives the user's sense of "I just did that" is worse than an extra read); Firestore offline persistence (rejected — it changes staleness semantics app-wide for a targeted problem).
* **Consequences:** The badge drops from 62 reads to ~1 on every navigation. Revisiting a screen within 30 seconds costs nothing. The remaining floor is ~250 reads for a genuinely fresh screen, which scales with the workspace and is the case for server-side rollups later. `src/tests/read-cost.test.ts` pins the de-duplication, the failure eviction, the narrowed queries and the declared index.

### ADR-015: A Purge That Keeps Configuration, and Refuses To Forget a Suppression
* **Status:** `ACCEPTED` | **Date:** 2026-08-28 | **Phase:** Phase 18
* **Context:** A test workspace accumulates data that makes every screen misleading — companies from trial runs, drafts written against an offer that has since changed, campaigns nobody remembers starting. Deleting the business and rebuilding it works but discards the offers, knowledge base, sender identity and API keys that took real effort to configure.
* **Decision:** `purgeBusinessDataCallable` deletes the prospecting collections for one business and keeps everything that describes how it works. Two exclusions are not offered as options: the **suppression list**, because someone who asked never to be contacted must stay suppressed and a purge that forgot them would let the SDR mail them again on the next run; and **spend history**, because it is an accounting record the budget guardrails read, not prospecting data. The business name must be retyped — an irreversible bulk delete behind one click is a delete that eventually happens by accident.
* **Alternatives Considered:** Deleting strictly by `businessId` (rejected on measurement — the live workspace holds 43 companies, 44 contacts, 32 outreach, 23 conversations and 5,747 logs with **no** `businessId`, and `matchesBusiness()` renders an unstamped document under whichever business is being viewed, so that purge would have looked like it did nothing); offering a "also clear suppressions" checkbox (rejected outright); a soft delete with an undo window (rejected — it keeps the documents that are being paid for and still counted by every query).
* **Consequences:** Unstamped documents are swept too, but **only while the workspace has one business** — with a second, "belongs to nobody" means "shows in both", and this purge has no mandate over the other business's screens. That sweep pages the workspace and filters in memory, since an absent field is not in any index; acceptable for an action a person triggers by hand and confirms by typing a name. `functions/src/tests/reliability/purge-business-data.test.ts` pins the exclusions, the confirmation, the recursive conversation delete and the batch bound.

### ADR-016: Live-Run Remediation — Five Defects Found by Leaving the SDR Running
* **Status:** `ACCEPTED` | **Date:** 2026-08-31 | **Phase:** Phase 18 (live-run remediation)
* **Context:** The SDR ran unattended on a real campaign from 28 to 31 August. It produced **nothing** after the first day: 116 companies discovered on 28 Aug, then 0 on each of the next three days; 62 drafts then 0; $0.35 of AI spend then $0. Meanwhile it failed 21 identical jobs every single day. Five distinct defects, each independently sufficient to stall the pipeline:
  1. **Discovery invented a search and then went silent.** `GooglePlacesDiscoveryProvider` fell back to hardcoded `["fleuriste"]` and `["Nantes"]` when the campaign named no keyword or city. The campaign brief was "tattoo shops in France" and the ICP translator returned `cities: []`, so a nationwide brief quietly became a one-city search, exhausted Nantes in a day, and returned "Created 0 leads" on twelve consecutive runs while still reporting `status: "active"`.
  2. **`company.website` was never validated.** Google Places returns whatever link a listing carries. On 78 companies with a website, four held a Waze live-map link, a `acceslibre.beta.gouv.fr` government accessibility listing, a 2015 WordPress portrait of the artist, and a `google.com/search?q=mailto:...` URL. Those fed the technical audit (scoring the wrong domain), the email scrape, and the contact-form channel — a live probe of 12 blocked companies returned two "submittable" forms, both on third-party domains, one of them a government service.
  3. **The contact-form channel was unreachable.** Channels were settable only at launch, so the running campaign carried `channels: undefined` → email only. 39 companies with a website and no published email dead-lettered daily as "no contact found".
  4. **Dead work was re-enqueued for ever.** `daily-research-runner.ts` re-selects companies by status with no outreach document. The permanent-failure verdict lived only on the job, so the same 21 companies were enqueued, failed and dead-lettered every day; 121 failed jobs had accumulated. The same file also attributed unstamped companies to a hardcoded `"biz_devcomm"` that does not exist in this workspace.
  5. **Schema validation discarded paid-for work.** 80 of 163 research runs failed — 49% — on `too_big` (a segment label of 100+ chars, an outreach field past 200) and one `invalid_type` for a missing narrative field. `z.string().max(N)` *rejects*; applied to model output that throws away a complete generation after it has been billed.
* **Decision:**
  1. The Places provider throws when it has no keyword or city rather than substituting its own. Areas resolve campaign → `settings.defaultDiscoveryCities`, and a campaign with none fails loudly (`discovery.campaign.no_area`). Areas rotate across runs via `areaCursor` so later cities are actually reached, and four consecutive empty runs set `areaExhausted` and log `discovery.campaign.area_exhausted` — a finished campaign says it is finished. The ICP translator is instructed that geography is mandatory, with a deterministic nationwide fallback to the twelve largest French cities.
  2. `isUsableCompanyWebsite()` gates the website at discovery; a rejected URL is kept as `directoryUrl` (having no site of their own is the need a web offer sells against) and never as `website`. `detectContactForm` re-checks independently, so existing bad data cannot reach a send.
  3. Channels are editable on a running campaign from its overview screen. Both non-email channels stay off by default.
  4. A permanent failure stamps `outreachBlockedReason` / `outreachBlockedAt` on the **company**; the daily runner skips those, and `contact-waterfall` clears the block the moment a contact is found. The hardcoded business fallback is gone.
  5. `functions/src/utils/ai-schema.ts` bounds model text by **truncation**. A length cap protects storage and display, which truncating satisfies completely. Fields that carry meaning stay strict: research with no `fitScore` is still refused, an email with no `body` is still refused, and an unrecognised `recommendedNextAction` falls back to `enrich_more` — never to "contact them".
* **Alternatives Considered:** Keeping a default city but making it configurable (rejected — the failure was silence, not the value; a campaign that cannot form its search must say so); dropping the third-party website instead of keeping it as `directoryUrl` (rejected — it is genuine evidence of the need); relaxing the schema maximums (rejected — it moves the cliff rather than removing it, and truncation is what a cap actually needs to do); defaulting a missing `fitScore` (rejected under Invariant 6 — a defaulted score is a claim about a prospect that no evidence supports).
* **Consequences:** `functions/src/tests/reliability/live-run-defects.test.ts` (21 tests) pins every one of them, using the exact URLs and payload shapes taken from the live run. Existing data is not retro-fixed: the four bad `website` values and the running campaign's empty `cities` predate the gate and need a one-off correction.

### ADR-017: Qwen as a Second AI Provider, via the Anthropic-Compatible Endpoint
* **Status:** `ACCEPTED` | **Date:** 2026-08-31 | **Phase:** Phase 18 (cost)
* **Context:** Measured AI spend across the whole project to date is **$0.75** (309,779 input + 88,722 output tokens at Haiku 4.5 list). That is not yet a cost problem, but the per-unit rate sets the ceiling on volume: at 500 companies/day the same pipeline is roughly $200/month. Alibaba's Qwen3.8-Flash lists at **$0.16 / $0.47 per million** against Haiku 4.5's **$1.00 / $5.00** — about 6x cheaper on input and 10x on output. Model Studio publishes an **Anthropic-compatible Messages API**: same `POST /v1/messages` shape, same `x-api-key` header, same `system` + `messages` body.
* **Decision:** Add `qwen` as a third `AiProviderName`, implemented as `AnthropicProvider` parameterised by base URL rather than a fifth copy of four near-identical request methods. `QwenProvider` changes three things — key, base URL, model — and every prompt, parser, schema and token counter is shared, which is also what makes an A/B meaningful: the only variable is the model. The provider is selectable from Settings alongside its key; the factory falls through to any configured provider and finally to `MockAIProvider`, so an unconfigured choice degrades instead of failing every company. Qwen list prices are added to `ai-pricing.ts` keyed by **provider**, because the model id alone would fall through to the Claude table and be billed ~6x too high.
* **Alternatives Considered:** The OpenAI-compatible Chat Completions endpoint Model Studio also serves (built first, then reverted — the Anthropic shape reuses the provider whose prompt handling and usage fields already match, so the diff is smaller and the A/B cleaner); a separate standalone `QwenProvider` duplicating all four methods (rejected — 169 lines of copy that would drift); switching the default to Qwen outright (**rejected** — see below).
* **Amendment (same day, at the owner's direction):** Qwen is now the **default** provider (`defaultSettings.aiProvider: "qwen"`), and OpenAI is removed from the Settings UI — the provider class and its place in the fallback chain are kept, it is simply no longer configured from a screen. The quality caveat below was raised before this change and the owner reaffirmed the decision; it stands as a known, accepted unknown rather than a resolved one. The fallback ordering makes it safe to ship ahead of the key: with no Qwen key configured, the factory still selects Anthropic.
* **Consequences:** The Settings panel says plainly that Qwen's French copy quality is unmeasured. That is the honest state: the pricing is documented and verified, the endpoint and model id (`qwen3.8-flash`) are verified against Alibaba's own documentation, and *nothing about output quality on French B2B prospecting copy has been tested*. No published benchmark answers it; only running both providers over the same prospects and reading the drafts does. `functions/src/tests/reliability/qwen-provider.test.ts` (10 tests) pins the endpoint construction — including the documented `/v1/v1/` 404 trap — that a Qwen model id is never rewritten by Claude's alias table, and that Qwen spend is priced at Qwen rates.

### ADR-018: Prompt Payloads Carry Facts, Not the Previous Call's Bookkeeping
* **Status:** `ACCEPTED` | **Date:** 2026-08-31 | **Phase:** Phase 18 (cost)
* **Context:** Outreach generation was sending **12,043 input tokens per draft**, five times the research prompt. Measured on a real prospect: the research document in that prompt was 4,454 tokens, of which `rawInput` (2,206) and `rawOutput` (1,123) were the request and raw HTTP response of the *previous* AI call being echoed straight back into the next one — 75% of the block, carrying nothing the parsed fields beside them already said. The company document was 1,109 tokens where the copywriter uses about 108. Both were serialised with `JSON.stringify(x, null, 2)`, paying for indentation on every company.
* **Decision:** `compact()` strips a named list of non-content fields (`rawInput`, `rawOutput`, `rawProviderData`, and internal plumbing) before a document enters a prompt, and the per-company payloads are serialised compactly. The hand-written output-schema example in the template stays indented — it is a fixed cost paid once per call and reads better to the model.
* **Alternatives Considered:** An allowlist of fields to send rather than a blocklist to strip (rejected for now — a new evidence field would silently stop reaching the writer, which is a quality regression that fails quietly; the blocklist fails loudly by sending too much); prompt caching (**measured and rejected** — Haiku 4.5 requires a 4,096-token stable prefix and these system prompts are 524 and 317 tokens, so no cache entry is ever created; it would only pay off on Sonnet 5, which costs 2x per token).
* **Consequences:** **3,842 tokens saved per draft**, about 32% of the measured prompt, with no quality tradeoff — nothing removed is a fact about the prospect; every removed field is bookkeeping about how a fact was produced. Also fixed: `DEFAULT_ANTHROPIC_MODEL` was `claude-3-5-haiku-20241022`, a 2024 model any deployment without an explicit setting used silently; the alias table now maps stored dated ids forward to current ones. `functions/src/tests/reliability/prompt-payload.test.ts` pins that raw payloads never re-enter a prompt while the grounding facts still do.

### ADR-019: Commercial Terms Are Offer Data, Checked Deterministically; Attribution Is Resolved or Refused
* **Status:** `ACCEPTED` | **Date:** 2026-11-10 | **Phase:** Phase 19 (Go-Live Readiness)
* **Context:** The first business going live sells a website with **no setup fee** and a 49 € HT monthly subscription over 24 months. The reply guardrail refused any draft containing "gratuitement" — so every honest description of that offer would have been escalated — while a 2-digit price slipped through an offer with disclosure off. Separately, 37 `|| "biz_devcomm"` fallbacks survived ADR-016 #6, pointing at a business id that does not exist in the live workspace; the daily research runner capped every business at 50/day whatever Settings said; and the daily-limit counters' composite indexes were neither declared nor deployed, so those limits never applied (an unreadable counter allows the work by design).
* **Decision:**
  1. **Terms are data on the offer** (`pricingGuardrails.setupFee | monthlyPrice | commitmentMonths | taxLabel | approvedTerms`), never words in code. `pricing-guardrail.ts` checks every draft against them: free wording only if a free component is declared, never a free *period* unless approved, no discount unless approved, no figure when disclosure is off and only declared figures when it is on, no contradicting commitment or tax basis. The same pure function runs on replies and on cold outreach (as an unsupported claim), and the same terms are stated to the model by `describePricingTerms`.
  2. **Attribution is resolved from related records or refused.** Contact → company → existing conversation; otherwise the record carries no business. Unattributed means: no AI reply (human escalation), no meeting booked, no outreach, no discovery run, no signal collection. Suppression (unsubscribe, bounce) never depends on attribution. Unattributed spend is recorded under a ledger bucket so it still counts against the budget.
  3. **Volume follows Settings, bounded per pass, counted atomically.** One `dailyUsage` counter per business per Paris day, reserved in a transaction before each AI call — no query, no index, exact under concurrency. Hourly runner, ≤ 50 enqueued per pass shared across businesses, per-business remaining budget for research and for generation. A job that hits a daily limit ends `deferred` and returns its company to the backlog.
  4. **The Settings editor may not alter what it saves.** Offer fields are replaced whole (`mergeFields`), and no form invents a price, model, metric, industry or proof.
* **Amendment (same day, after an adversarial review FAIL):** the first guard matched fixed phrasings and let 21 of 46 misstatements through; it now judges free wording per clause by proximity, handles negation, and refuses undeclared commitments and tax bases. The first volume fix relied on query counters that could not see most research; replaced by the atomic counter above. Cold outreach was validated against no offer in the real pipeline (wrong campaign collection); fixed. The context builder no longer falls back to the workspace's default company text, which named one firm.
* **Amendment 2 (same day, after a second FAIL):** a reviewer wrote 60 new misstatements and 52 passed the detector. Conclusion recorded here: a deterministic French pattern check can find known misstatement shapes but cannot certify a draft. `checkPricingStatements` is therefore **advisory** (shown to the human reviewer), and the safety property moves to a **fail-closed gate**: `mentionsCommercialTerms` — broad vocabulary — blocks autonomous reply dispatch and automatic cold-email approval for any draft touching commercial terms. Commercial terms reach a prospect unattended only once code, not the model, writes them (Phase 20: offer summary and checkout link inserted by code). The same review found that replies were marked sent without any delivery, on all three reply paths. All three now go through `deliverReply` (suppression re-checked, delivery reported); with no `ReplyTransport` implemented yet, autonomous replies go to a person and manual ones are recorded as not sent, with the Inbox saying "à envoyer depuis Unibox". A third review found the gate's stems ASCII-only (`\w`), missing accented forms; fixed and pinned.
* **Alternatives Considered:** Adding "gratuit" to an allowlist per business (rejected — business-specific branching by another name, and it would not stop "premier mois offert"); letting the model self-report `pricingGuardrailPassed` (rejected — the model is the thing being checked); attributing unattributed records to the only business when a workspace has one (rejected — HANDOFF State contract #5 already limits that to purge, and a second business makes it wrong silently); raising `Math.min(limit, 50)` to a bigger constant (rejected — a constant per invocation is right for Invariant 7, the error was running the job once a day).
* **Consequences:** Phrases like "un échange sans engagement" are now flagged on an offer with a commitment — deliberately: the prospect cannot tell which engagement is meant. Daily limits become real at deploy; owners who relied on the de-facto 50/day must set the limit they want. True-but-undeclared figures (a 24-month total, a TTC conversion) are escalated by design. `functions/src/tests/reliability/go-live-readiness.test.ts` (80 tests) and `src/tests/offer-form.test.ts` (9 tests) pin all of it, including a static scan for hardcoded business fallbacks and a self-consistency check that the seeded offer passes its own guardrail.

### ADR-020: Social DMs Are Sent From a Local Browser Session, One Key per Message
* **Status:** `ACCEPTED` | **Date:** 2026-11-10 | **Phase:** Phase 23 (Social DM Sessions)
* **Context:** The owner prospects by Instagram/Facebook DM today with a ChatGPT agent driving Chrome and wants it inside the SDR with Qwen, for both networks, with replies handled in conversations, starting the same day. Until now the SDR deliberately never sent DMs (`social-dm-generation.ts`: "Automated DMs breach every platform's terms") and a person copied each message by hand. Constraints found while mapping the code: Meta's terms prohibit automated access and restrict accounts that are detected; the official Instagram messaging API only lets a business reply to people who wrote first; a Facebook DM sent from a personal profile to a business Page gets its answer in personal Messenger, which no API exposes; the reply pipeline is email-shaped (required email, Instantly ids, booking invites by email).
* **Decision:**
  1. **A local runner** (`social-runner/`, Node + Playwright on the owner's Mac) drives a visible browser with a dedicated persistent profile in which the owner logs in once. It types each prepared DM into the prospect's conversation and **sends only after the person presses Enter for that message**. It never sends unattended, never uses stealth plugins, proxies or several accounts, and stops — without retrying — on any login wall, checkpoint, CAPTCHA or "action blocked" page.
  2. **Replies are swept from the inbox by the same runner** (both networks, today), fed to a social-specific ingestion path that reuses classification, unsubscribe detection, the grounded reply generator and the offer checks, and are sent with the same one-key rule. The email router, dispatcher and booking path are never used for social conversations (they would email a handle or invent a calendar invite). The official Instagram API remains a later option (reply-only; needs a Meta app).
  3. **The runner uses the Firebase Admin SDK** with ADC pinned to `devcomm-os` and calls compiled services from `functions/lib`, like the existing operator scripts — not an authenticated callable as the first draft of the Phase 23 spec said. It is an operator tool on the owner's machine; it refuses any other project and the emulator host, and the AI key is read server-side as it is for every other script.
  4. **Pacing is data:** per business, per network `socialLimits` (defaults 30/day, 45 s between sends), reserved atomically in `dailyUsage`; one first DM per company ever (`company.socialDmSentAt`), suppression by handle (`social_handle`), company `doNotContact`, domain and SIREN checked right before every first DM and every reply.
* **Alternatives Considered:** A fully unattended bot (refused: the owner's showcase account carries the risk, it is unsolicited bulk messaging, and the per-message key costs ~10 seconds); copying the ChatGPT agent approach of letting the model click Send (refused for the same reason — the model never decides to send); the official APIs only (rejected for today: no Facebook path from a personal profile, and a Meta app setup is needed for Instagram).
* **Consequences:** Account risk is the owner's and scales with volume; caps default low and are adjustable. Selectors depend on Meta's UI: role-based selectors in FR/EN, every failure stops the session with a reason rather than guessing. The guarantee "nothing is sent without a person" is enforced in code (session state machine test) and documented in the runner README.

### ADR-021: Offer Experiments — One Variant per Prospect, Terms Stated by Code
* **Status:** `ACCEPTED` | **Date:** 2026-11-10 | **Phase:** Go-live operations (after Phases 19 and 23)
* **Context:** The owner asked to A/B test several commercial terms for the same website ("fixe élevé, petit abonnement… essaye un peu tous les prix") and adapt later. The engine knew one offer per company (`company.offerId`, set by discovery) and the business's knowledge base stated the control offer's price in every prompt, so any variant would have been contradicted by its own FAQ. After the first 139 live DM drafts, a second problem showed: the model stated the price in about a third of them, left it out of the rest, and paraphrased it when it did ("sans frais initiaux", a monthly figure without its tax basis or commitment). An experiment measured that way compares the model's moods, not the offers.
* **Decision:**
  1. **The experiment is data on the business** (`business.offerExperiment = { id, offerIds, status }`). A never-contacted prospect is assigned one variant the first time a message is drafted for it — `sha256(experimentId|companyId) mod n`, in a transaction, stored as `company.offerAssignment` — and keeps it for the whole conversation. A prospect already contacted is never re-assigned. Assignments outlive the experiment: stopping it assigns nobody new, and the assigned keep their offer. A draft written before the experiment keeps the offer it pitched.
  2. **Terms live only on each offer.** While an experiment exists, any knowledge-base pricing rule or FAQ that states a figure or contradicts the offer being pitched is withheld from the prompt (`offerNeutralKnowledgeBase`); the seed refuses to write if the knowledge base states an amount.
  3. **Code, not the model, states the terms of a first DM.** An offer may declare `pricingGuardrails.termsLine`, one sentence written by the business. When it is usable (`approvedTermsLine`: disclosure allowed and the sentence passes `checkPricingStatements` against its own offer), the model writes only an opening and a closing question, never sees a priced line of the offer (`offerWithoutTerms`), and code composes opening + terms line + question. The model's text is checked for any money talk (`modelCopyIssues`); one redraft if it fails or a part is missing, the better draft is kept and what is still wrong is shown on the draft. A line that contradicts its offer is not used and the draft says why. The seed refuses to write an experiment unless every offer, control included, carries a usable line that states its declared figures and commitment.
  4. **Results by variant** come from `offer-experiment-report.mjs` (read-only; funnel per variant over sent).
* **Amendment (same day, two adversarial reviews, both FAIL then fixed):**
  1. Round 1 found website-specific closing-question shapes in the generic prompt (Invariant 1), `--redraft` able to overwrite a DM a person had edited (edits keep the status "draft"), money talk passing the model-text check ("c'est cadeau", "rien à débourser", "49 balles") and false alarms on ordinary openings ("couture", "abonnés", "remise en forme"), and a pre-existing `$'` expansion in the prompt `substitute()` that let a company name write outside `<untrusted_prospect_content>`.
  2. Round 2 found that the first fix's prospect-fact mask ("votre … offert", "votre engagement …") hid OUR most natural misstatements ("votre premier mois offert", "votre engagement de 24 mois") — a DM addresses the prospect as "vous", so a possessive cannot tell whose fact it is. The mask is now limited to shapes that cannot describe our offer (a commitment *to a cause*, never before a figure or "nous"; what *they* give, with them as the subject) and to free items the verified facts themselves state, never near a period word. It also found: a hand edit erasing the generator's warnings; a redraft racing a send or an edit (now refused by `onlyIfUnreviewed` and a `lastUpdateTime` precondition); the runner showing the review listed at session start rather than the one of the text it types; DM facts reaching the model without labels; one-pass placeholder substitution and "<" escaping needed for untrusted JSON; a forced email regeneration able to take over a DM draft.
  3. One review function (`reviewSocialDmText`) now serves generated and hand-edited DMs.
* **Amendment 2 (same day, after a third review broke the narrowed masks too):** the masks are removed. Distinguishing our claims from the prospect's facts in the same words is not solvable by grammar in a "vous" message, and every exception was a hole ("offerte par l'équipe", "ni frais ni engagement", a prospect fact "site gratuit" clearing our "votre site offert"). Final design:
  1. **A closed vocabulary.** The model's part must not contain any commercial word (gratuit, offert, offre, frais, prix, payer, régler, mois, engagement, contrat, essai, remise, promotion…), whoever it is about; the prompt lists them as forbidden, so a match means the model disobeyed and the draft is rewritten. Prospect facts are said in other words.
  2. **A model judge** (`social-dm-judge.ts`) reads the opening and question for paraphrases no list foresees ("vous ne sortez rien de votre trésorerie au départ"): temperature 0, text wrapped as untrusted, fail-closed (an unavailable judge marks the draft for the operator's confirmation, never as checked). Verified live on Qwen, including an embedded "ignore tes consignes" attempt.
  3. The shared detector (`checkPricingStatements`, also used for email and replies) gained the commitment wording and lost the "offert par <anyone>" exemption the review found.
  4. The runner no longer sends a text the stored draft changed away from after it was shown, and a send records the text actually sent.
  5. A fourth verification (FAIL → fixed) found: a person's one-word edit erased the judge's verdict (the edit path now re-runs the judge, fail-closed, and refuses to write over a draft changed since it was read); words caught that the prompt never forbade ("gracieux", "j'essaie", "si chers") — the prompt's forbidden list is now generated from the same table as the check, and a test holds the two together; commitment VERBS read as durations in emails ("nous nous engageons à livrer en 2 mois") — a verb now states a commitment only as "s'engager sur/pour N mois"; the judge now neutralises tags in the text it reads; an experiment draft whose offer has no usable terms line now requires the operator's confirmation.
* **Alternatives Considered:** Letting the model state terms with stricter instructions (rejected — on 139 live drafts the price appeared in about a third, not always in approved words; instructions narrow that, they do not close it); validating the model's figures and refusing drafts without them (rejected — it still decides the wording, so two prospects of one variant read different terms); assigning variants by campaign (rejected — campaigns differ by sector and city, which would confound the comparison); random assignment at send time (rejected — a retried draft could change offer).
* **Consequences:** Every first DM of a variant states the same terms, word for word, which is what makes the comparison valid. The terms line is editable in Settings → Offer (it is part of the guardrail object the form replaces whole, so it is never silently dropped). Email first messages do not use the terms line yet. Bloomy variants live on 2026-11-10: A 0 € + 49 € HT/mois 24 mois (control), B 0 € + 29 € HT/mois 36 mois, C 490 € HT + 29 € HT/mois 12 mois, D 1 490 € HT + 15 € HT/mois sans engagement. Pinned by `functions/src/tests/outreach/offer-experiment.test.ts` and `social-dm-terms.test.ts`.

### ADR-022: A DM Goes Only to an Account That Is Provably the Prospect's
* **Status:** `ACCEPTED` | **Date:** 2026-11-10 | **Phase:** Go-live operations (social DMs)
* **Context:** Checking the live queue before the first real session showed DM drafts addressed to `facebook.com/teamfresha` (10), `instagram.com/fresha` (5), `kipik.ink` (4), `mappyofficiel` (3), Flickr, a food critic, a theatre, a design blog. The profiles came from the links on the page discovery recorded as the company's "website" — often a booking page or a directory, whose links are the platform's own accounts. Nothing checked that the account belonged to the company.
* **Decision:** `profile-trust.ts` decides, purely: a known platform/directory account is never the prospect's; a handle matching the company's name is trusted; a profile scraped from a directory page is rejected; a profile scraped from the company's OWN site (a site whose address matches the company's name, or a link-in-bio page) is trusted when its handle matches that site or is a numeric id; anything else is uncertain and not used. A profile the listing names directly is trusted unless it is a platform account. `resolveCompanySocialProfiles` applies it (so new drafts only target trusted accounts), the runner's gate refuses a draft whose stored account is a platform or directory one, and `repair-social-dm-recipients.mjs` re-points existing drafts (a handle trusted for two companies is dropped too).
* **Alternatives Considered:** a platform blocklist only (rejected — the theatre, the blog and the critic are on no list); name similarity only (rejected — generic listing names like "Salon de Tatouage" match nothing, and one such name pointed at a design blog, so a generic name vouches for no site); asking the operator per draft (kept for later — uncertain profiles are set aside, not guessed).
* **Consequences:** On 2026-11-10 the repair re-pointed 24 drafts to the prospect's own account and set 29 aside (no trusted account; status "rejected", reason `no_trusted_social_profile`, text kept): 110 DM drafts remain, all to trusted accounts, none shared. A few real accounts are lost (an artist's personal handle on the studio's site, a generic listing name) — the cheaper mistake. Pinned by `functions/src/tests/social/profile-trust.test.ts` (cases from the live audit) and the gate test in `outbound.test.ts`.
* **Also added:** `npm run social:rehearse` — a session rehearsal on the real account that types, sends and records nothing (`social-runner/src/rehearsal.mjs`), and the `outreach(status, sentAt)` index the email send limit needs (found by a live audit; not yet hit since nothing is emailed).

### ADR-023: A Prospect With No Channel Is Searched For, Then Left Alone — Never a Failing Job
* **Status:** `ACCEPTED` | **Date:** 2026-11-11 | **Phase:** Go-live operations (live run, day 2)
* **Context:** After a night of autonomous running, 22 of 60 qualified prospects had no email and no social profile linked from their site, and the hourly runner re-queued an email draft for 12 of them that could only throw ("Lead is not ready for outreach") — failed jobs, shown as errors, every hour. Most of these businesses (tattoo studios, barbers) are active on Instagram; their profile is simply not linked from the page discovery recorded.
* **Decision:** (1) A draft task for a company with no email tries the campaign's other channels (DM, then contact form); if none exists it logs `outreach.no_channel` once as information and stamps `noChannelAt`; the runner waits 7 days before offering the company again. (2) Before deciding there is no channel, `findInstagramBySearch` runs one Google search (Serper) `site:instagram.com "<name>" <city>` and accepts the first result whose handle matches the company's name (ADR-022 rule) AND whose title/snippet confirms the place by phone, postcode or city. A city is weak evidence, so with the city alone the handle must be the business's whole name, with nothing around it but trade words, the city or digits (`carriesWholeName`, segmented by the best split so "tattooshop" is "tattoo"+"shop"). The resolver re-applies the rule to the stored profile, so the rule that accepted a profile is also the rule that lets it be used.
* **Alternatives Considered:** accepting the first Instagram result (rejected — the same name exists in other towns: "@barber_avenue_73 · Aix-les-Bains" for a Paris barber); name match + city only (tried first, rejected by the live run: "Kustom Tattoo" in Paris matched "@kustomtashoes", a Paris sneaker customiser); reading the Instagram profile page to confirm (rejected — logged-out scraping of Meta, against ADR-020's no-stealth rule); asking a model whether the result is the right business (rejected — search snippets are untrusted text and the facts needed are exact strings).
* **Consequences:** On 2026-11-11, 12 no-channel prospects were searched: 9 profiles kept (4 confirmed by phone or postcode, 5 by city with the whole name), 1 namesake refused after the rule was tightened (its draft set aside), 2 not confirmed. Some real accounts are missed (an abbreviated handle confirmed only by the city) — the cheaper mistake, as in ADR-022. Pinned by `functions/src/tests/social/profile-search.test.ts`, the resolver cases in `outbound.test.ts` and `functions/src/tests/research/no-channel.test.ts`.

### ADR-024: Automatic Send Sessions for First DMs — Amends ADR-020's One-Key Rule
* **Status:** `ACCEPTED` | **Date:** 2026-11-11 | **Phase:** Go-live operations (social DMs) | **Amends:** ADR-020 (decision 1)
* **Context:** ADR-020 refused unattended sending: every DM needed the operator's Enter. On 2026-11-11 the owner, who already sends Instagram DMs with an automated agent, asked again and explicitly for the SDR to send them automatically, on their own account. Since ADR-020, a first DM's commercial terms are written by code and its text is checked by a closed vocabulary and a model judge (ADR-021), and a DM only goes to an account proven to be the prospect's (ADR-022, ADR-023). What did not change: Meta's terms prohibit automated messaging, and the account that sends carries that risk. That risk is the owner's to take; it is stated in the runner's README and was stated to the owner.
* **Decision:** `social:send --auto` starts an **automatic send session** — Instagram only. The operator starts it in a terminal and confirms the account; then each first DM is typed once, shown, and sent when a countdown ends (10 s by default, `--veto 5…300`, never under 5 s) unless S (skip) or Q / Ctrl+C (stop). It is the same code path as a send with a key — same gate, daily cap, spacing, blocker checks, journal and record — with the Enter replaced by the countdown, and stricter rules because nobody may be watching:
  1. **The SDR decides which text may leave unread** (`autoSendVerdict`, server side, on the same snapshot as the text typed): its checks passed with no warning; its commercial terms are the offer's own terms line, placed by code as a paragraph of its own and still in the text exactly once (a draft whose terms the model wrote always waits for a person); it passes the second-pass claim validation (`validateOutreachClaims`: reviews, rating, staff, a score, a town must match verified evidence; no prohibited promise, no undeclared term); and every figure the model wrote is exactly one a verified numeric fact of the prospect holds (a count, a rating, a score, a year — never the digits of a phone number, a registration number or an address) or a number of its own name or town, with no quantity spelled in words (`dm-figures.ts`). Anything else is `held`: not opened, not typed, left in the queue for a session with keys. The verdict is asked again right before the send. It fails closed.
  2. **The SDR's switch decides whether to send at all** (`checkAutoSend`): refused while `automationPaused` or safe mode is on; for 48 h after the network stopped a session of that business on that network; and after an automatic session stopped on a doubt, ended in a way nobody planned or never recorded its end, until a person has since finished a session with keys in which they sent or skipped at least one message. Asked at start, before each prospect and before each send — again after the wait between two DMs, so it is true at the moment of the send.
  3. **A first message only goes into a conversation that holds nothing** (`threadState`): the SDR only remembers what it sent itself, and the account may have written to a prospect by hand or with another tool. "New" is said only on positive evidence — the window's header is in a known interface language and every line of the chat window is that language's own label or the recipient's name, as read live on Instagram on 2026-11-11 — before typing and again right before the send; a check that still says "new" after a send is blind and stops the session. A draft whose conversation is not provably new is marked as left to a person (`autoHeldAt`): it stays in the queue of a session with keys and no automatic session opens that profile again; three such conversations in a row stop the session (the check no longer recognises the window). A network without this check (Facebook today) cannot run an automatic session.
  4. **Doubt stops the session; nothing is typed twice.** A text that does not land in the composer as written, or changes there, stops the session. A text that leaves the composer without its bubble showing (a key typed in the browser window, a closed chat) is recorded "to check" — which takes the one-first-message lock — so no later session can send it a second time; unless a blocker page explains it (the session stops as blocked, nothing recorded) or the page merely rebuilt the composer with the text still in it (emptied, nothing recorded). A send not seen in the thread, any blocker page: the session ends. A stop request is honoured up to the instant before the send.
  5. **Replies are never automatic** (`social:inbox` has no such mode; `composeAndSend` only honours `auto` from the first-DM caller).
  6. **Every automatic send is recorded as one** (`outreach.sentAuto`, `auto` on the session, in the activity log and in the pending-send journal); a message a person's key sent is not.
* **What stays refused (ADR-020 unchanged):** stealth plugins, proxies, several accounts, randomised "human" behaviour, CAPTCHA solving, retrying after a block, running without a terminal or on a schedule, a model deciding to send.
* **Known limits, stated rather than hidden:** the checks of what a text says about a prospect are deterministic: every figure, the towns the validator knows (29), promises and commercial terms — not a free-form remark without a figure ("vos réalisations sont soignées", a town outside the list). The figure check compares numbers, not what they count: "5 ans d'expérience" passes for a business rated 5. It also holds harmless figures ("10 minutes", "7j/7"), which costs throughput only. The prompt only gives the model verified facts, and the model judge reads the opening for commercial content, not for truth. An operator who empties the composer by hand in the browser window and then presses S gets a "to check" record: it cannot be told from a message sent and not drawn yet (use S alone to skip). The "new conversation" check knows Instagram's French interface as of 2026-11-11; a change there makes it say "not new" (drafts set aside), never "new". The thread check cannot see a conversation the prospect deleted on the account's side.
* **Alternatives Considered:** keeping the one-key rule (rejected by the owner: the key per message is the step they want removed); sending without any countdown (rejected — it costs seconds the spacing rule already imposes, and keeps a way to stop one message); a scheduled background job (rejected — a session nobody started is the unattended bot ADR-020 refused); auto-sending drafts with warnings (rejected — the warning exists because a person must read that text); retyping a text that left the composer (first version, rejected by the review: it sent a second copy when the first had left from the browser window).
* **Consequences:** The owner can send the day's first DMs with one command. The account risk rises with automation and is not mitigated by concealment: if Meta objects, the session stops, automatic sending stays off for 48 h, and the account bears the consequence. No real DM has been sent yet by any session: the first automatic session should use `--max 3`, watched. Found on the way: the claim validator read evidence keys the providers do not write (`google_places_review_count` vs `google_review_count`), reporting every true review count as unsupported — fixed for emails and DMs alike. Reviewed adversarially in three passes (first FAIL: a stop request ignored after the countdown, a duplicate after a browser-window send, a stale gate after the spacing wait, a model-written-terms path, no thread check — all fixed; second PASS with three majors erring toward not sending: a phantom "sent" record hiding a blocker, a thread check that could set aside a whole queue, ratings not read in live phrasings — all fixed; third PASS, its residual — identifiers on record vouching for invented figures — fixed). Pinned by `social-runner/test/auto-send.test.mjs` (incl. a 300-seed sweep with browser keys and interrupts; every rule removed in turn makes a test fail), `social-runner/test/thread-state.test.mjs` (live samples) and `functions/src/tests/social/outbound.test.ts`.

### ADR-025: A First DM Opens a Conversation — the Sender's Own Introduction, No Commercial Term, and What Is Said of the Prospect's Site Is Written by Code
* **Status:** `ACCEPTED` | **Date:** 2026-11-11/12 | **Phase:** Go-live operations (social DMs) | **Amends:** ADR-021 (decision 3) for a business that opts in; ADR-024 (decision 1): a second kind of draft an automatic session may send, and every code-written sentence is now checked against its source at verdict time
* **Context:** After the first two real DMs (one sent with a key, one by an automatic session), the owner judged the messages "trop démarchage" and asked for the best reply rate, with research, sent from a personal account as the studio's co-founder. The messages were a compliment, "we design sites for craftsmen like you", the offer's price line (ADR-021) and a question — about 60 words and a price to a stranger. What the practitioners' guides found agree on (vendor and agency sources, no controlled study — directional only): a first message is short (three lines), names one specific true detail, carries no pitch, price or link, and ends on one easy question; a pitch in the first message is the weakest category in the one dataset that separates it (3 % vs 31 % for researched, personal openers). For prospecting between professionals the CNIL's guidance (read 2026-11-11) asks no prior consent when the message concerns the recipient's profession, but each message must let them "prendre connaissance de l'identité de l'organisation qui l'émet" and refuse further ones "par un moyen simple" — the SDR already reads "stop" in replies and suppresses the handle; the message itself did not say who wrote.
* **Decision:**
  1. **The style is data on the business** (`business.socialDmOpening = { style: "conversation", introLine, observations? }`, set by `functions/scripts/set-social-dm-opening.mjs`). Absent, nothing changes: the offer's terms line, as in ADR-021.
  2. **Up to four parts, two of them written by code.** The model writes an opening (a greeting and one good, true thing about the prospect, 8–22 words) and one question (≤ 14 words, never a call or a meeting, never naming what we do again). Between them, in the opening's paragraph, code inserts — word for word — at most one **observation** about the prospect (decision 4) and the business's own **intro line**: who writes and what the business does. The model sees neither. An intro line that is not a sentence on one line (20–220 characters, 4 words), that carries a link or a number to call, or that touches commercial vocabulary is refused: the draft falls back to the terms line and says why.
  3. **No commercial term in the message.** The model's parts are held to the closed vocabulary and the model judge of ADR-021, as the parts around a terms line were. The prospect is still assigned its experiment variant at drafting time: the terms come in the reply to someone who answered (`social-inbound.ts`, `resolveConversationOfferId`), which a person reads and sends with a key.
  4. **What the message says of the prospect's online presence is written by code, from the evidence, or not at all** (`social/dm-observations.ts`). `pickObservation` states the first of the kinds the business asked for that the verified evidence says plainly, with no sign to the contrary — no site of their own, a site measured slow on a phone (with the measured figure), a site unfit for phones, a site no longer updated, no online booking — as one fixed sentence. A key recorded both ways says nothing; "their site" needs a positive sign that the address on record is theirs — it passes the third-party lists; it is the root of a registered domain (not a subdomain a platform hands out, no parameter but a listing's tracking ones) or a page of a host registered under two words of the business's name (one shared word is usually their trade: "tattoo" in tattoodo.com); our crawler stayed on that site; and the speed figure was measured on it — because "not on a list of platforms" is not such a sign (two live prospects' recorded "website" was a directory page on wanderboat.ai and ivof.com); a platform flag beside an address that is positively theirs is a contradiction and says nothing; "no address on record" is contradicted by an own address on the company record or any measurement of a site; a page our crawler could not fetch states nothing at all. **Only two kinds may leave unread: no site of their own (a platform flag, or no address and no sign of a site) and a slow site (Google's own test, with its figure).** The other three rest on heuristics of our page reader that were built to feed a score and are false on ordinary pages; they are written for a person to check (`observation_needs_person`). **The model is kept off the subject:** its two parts may not contain a word of a closed vocabulary (`PRESENCE_TABLE`: site, page, online, booking, phone, display, speed, redesign, update, search, link, visitor…), listed in the prompt like the commercial words, and it is not handed any evidence about a web page.
  5. **What the opening may be built on** (`conversationFacts`): the prospect's reputation and trade. No fact that identifies, locates or registers the business (the first drafts opened "vous êtes situé au 55 boulevard…"), no year or date, nothing the company register says of its size (matched by name: a studio was told it had a namesake's four establishments), nothing about its web page. `extractPersonalizationFacts` words the keys the providers really write (a rating with its number of reviews, a decimal comma).
  6. **An automatic session may send a conversation draft** (`autoSendHoldReason`, `conversationAutoHoldReason`, `autoSendVerdict`) when: its checks passed with no warning; the intro line and, if the draft carries one, the observation are in the text exactly once, the observation right before the intro line; the text, read again at verdict time whatever the stored review says, touches neither the closed commercial vocabulary nor the broad one of ADR-019, and its model parts no word of the presence vocabulary; **each code-written sentence is the one its source says today** — the intro line is the business's current, approved line, the observation is what `pickObservation` yields now from the current evidence for a kind the business still asks for (and, on the terms-line path, the terms line is the offer's approved line: a draft cannot vouch for its own exemption — its fields are writable from the app); every figure is a verified one; no prohibited promise stands anywhere, the business's sentence included. A draft carrying both styles' sentences is held. Everything else in ADR-024 is unchanged.
  7. **A draft an automatic session would hold says why on the draft** (generation and a person's edit): a word of either closed vocabulary is named, and a clean-looking draft the verdict would still hold gets "Ne part pas en automatique : …". A clean-looking draft that never leaves is a bug.
* **How it got there (same night, two adversarial reviews, both FAIL):**
  1. *First version:* the model wrote about the prospect's site from the site facts it was given, and a phrase check held "vous n'avez pas de site" without evidence. Review 1: the verdict trusted the draft's own intro line (a draft whose "intro line" was the whole message passed with a wrong town, an invented figure and a prohibited promise); 49 of 59 rewordings of a site claim passed; a person's edit erased the warning; the terms-line path had become stricter in silence; a broad-vocabulary word left a draft clean-looking and held forever; "votre studio" was flagged as a second introduction.
  2. *Second version:* the intro line compared with the business's, and the site check rebuilt by topic and polarity (a sentence about their site with a negation or a defect word is a claim). Review 2: 57 of 66 new rewordings passed ("ils méritent un vrai site", "votre site pourrait être plus rapide" — no negation, no defect word), 18 of 53 harmless sentences were held, a claim passed on another kind's evidence, a measurement of a social address vouched for "their site", and the terms path still trusted the draft's own terms line.
  3. *Third version (the design above), review 3:* sound, and no way found around the verdict — but three of the five code-written sentences were false on ordinary pages run through the real provider ("plus mis à jour" from an icon library's "Copyright 2023" in a page whose footer said 2026; "pas adapté au téléphone" from a viewport tag written without quotes; "pas de prise de rendez-vous" next to a "Réserver" link to an unlisted platform), a platform no list knows was "votre site", and the model was still handed the address, the "needs" and the "angle" research derived from the page. Fixed: two kinds leave unread, the address needs a positive sign, the model gets the name and the town.
  4. *Review 4: PASS, no blocker.* Two majors on which page "votre site met N secondes" is attributed to, fixed after the verdict and pinned by tests and mutations but not reviewed again: one word of the name in a platform's own name counted as "theirs" (tattoodo.com for "Lonestar Tattoo"), as did the root of a platform's subdomain; and the figure on file was not tied to the address it was measured on (a record corrected since keeps the old figure for a month).
  5. *Conclusion, the same as for commercial terms (ADR-019, ADR-021):* a French pattern check can find the shapes it was shown and cannot certify a text. What must be true is stated by code; the model is kept off the subject by a closed vocabulary; the verdict recomputes every code-written sentence from its source.
* **What stays refused, asked again the same day:** making the session look like a person to the network — randomised typing or pauses, reaching a profile through the search box instead of its address, mouse movement, anything whose purpose is that Meta does not recognise an automated session. ADR-020 and ADR-024 are unchanged on this. What the SDR does instead is what lowers the risk in the open: few messages a day, spaced, stopped at the first objection from the network, and a message a stranger has a reason to answer.
* **Known limits, stated rather than hidden:** nothing proofreads the French — among the first drafts one opened "vous avez 3 étables"; a model asked to proofread (same provider, temperature 0) found none of four such errors and was not shipped; a countdown shows each text for 10 s. An innuendo about their online presence that uses no word of the list ("ça rame chez vous") is not detected; the model has no web fact to build one on. A commercial hint that passes both word lists ("Rien à signer", "Sans carte bancaire") rests on the model judge alone, as in ADR-021/024, and here it would be the only term the prospect reads. The presence vocabulary over-holds ("visiblement", "rapidement", "trouver"): redrafted once, then named on the draft. An observation is as good as its evidence: "no site of your own" is said on "only a page on a platform" or on "no address on record and no sign of a site" — and nothing records that anyone looked for one, so it is false exactly when their site exists and is not on record (Google lists their Instagram): "sauf erreur de ma part" is the only cover; the rule that decides whose address it is rejects some real sites (a deep page under a brand unlike the domain, a two-part ending such as .co.uk) — silence, not a wrong sentence; "your site takes N seconds" is one lab measurement by Google's test, attributed to it. The second-introduction check still flags a name made of ordinary words ("Atelier Nord" + "du Nord") — a warning, not a wrong send. The offer experiment no longer compares variants on the first message (it is the same for all four): it compares them after a reply, where the terms are worded by the model and read by a person — the terms line is not inserted in replies yet. Reply rates per style are not comparable yet either: two DMs were sent in the old style.
* **Alternatives Considered:** keeping the price line and softening the copy around it (rejected — the price to a stranger is the pitch); a first message with no introduction at all, only a question (rejected — a stranger must be able to tell who writes and why); letting the model write the introduction (rejected — it would vary, could be wrong about who writes, and puts a person's name in a prompt); letting the model write the observation and checking it (tried twice, see above); a second model as judge of "does this speak of their site" (not tried — the same provider's judge missed every error of a simpler proofreading task that night); A/B-testing the two styles on the 29 drafts at hand (rejected for now — too few; `promptVersion` is stored on each draft so the comparison can be read later); a per-campaign intro line (later, if campaigns for different trades run side by side).
* **Consequences:** Live on 2026-11-12 (biz_bloomy): intro line set, observations `no_site, slow_site`; 29 unreviewed drafts rewritten (34–60 words, against about 60 with a price), all 29 allowed by `autoSendVerdict`, 8 with a code-written observation (7 slow site with its figure, 1 no site); 8 other prospects have a measured page that is not positively their own site, or an ordinary loading time, and get no observation. After changing a business's intro line, its observations, an offer's terms line, or after evidence is collected again, the drafts concerned wait (`*_not_current`) until rewritten with `backfill-social-dm-drafts.mjs --redraft`. Pinned by `functions/src/tests/social/dm-conversation.test.ts` and `dm-observations.test.ts`; 57 mutations of the rules, each failing a test; the Invariant 1 scan covers the conversation module and prompts (the observations module reads web evidence by design and names no business).
